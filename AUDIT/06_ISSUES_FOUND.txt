ISSUE-001
--------------------------------------------------------------------------------
Severity:      HIGH
Category:      Deprecated API / Future Error
Description:   app/mt5/account.py used datetime.utcfromtimestamp() and
               datetime.utcnow() — both deprecated in Python 3.12 and scheduled
               for removal in Python 3.14+. Would cause DeprecationWarning in
               3.12, RuntimeError in future versions.
Root Cause:    Code written before Python 3.12 deprecation policy tightened.
Affected File: app/mt5/account.py lines 245–246
Impact:        Broker server UTC offset detection would break on Python 3.13+,
               preventing correct daily loss limit reset alignment.
Fix Applied:   Replaced with datetime.fromtimestamp(ts, tz=timezone.utc) and
               datetime.now(timezone.utc). timezone already imported.
Test Required: Existing test_detect_server_timezone_returns_integer covers this.
Status:        RESOLVED

--------------------------------------------------------------------------------
ISSUE-002
--------------------------------------------------------------------------------
Severity:      MEDIUM
Category:      Observability / Silent Failure
Description:   4 bare "pass" exception handlers in app/automation/main_loop.py
               (lines 435, 452, 485, 491) swallowed exceptions with zero logging.
               Helper methods _fetch_current_prices, _fetch_spread_pips, and
               _build_risk_context would silently fall back to defaults without
               any trace that an MT5 API error had occurred.
Root Cause:    Bot loop design correctly avoids crashing on transient MT5 errors,
               but logging was omitted during Phase 11 implementation.
Affected File: app/automation/main_loop.py
Impact:        Impossible to diagnose transient MT5 connectivity issues from logs.
               Operator would not know why spread/equity values appeared stale.
Fix Applied:   Added logger.debug() before each pass, capturing the exception
               message and symbol context.
Test Required: No new tests needed — behavior is defensive by design; logging
               is verified by log output during live operation.
Status:        RESOLVED

ISSUE-003
--------------------------------------------------------------------------------
Severity:      MEDIUM
Category:      Security / Information Disclosure
Description:   All 9 exception handlers in app/dashboard/api/routes.py returned
               {"error": "internal error", "detail": str(e)} in HTTP 500
               responses. str(e) can expose internal file paths, database schema
               details, column names, and Python module structure to any client
               that can reach the dashboard.
Root Cause:    Development-era debug responses not hardened for production use.
Affected File: app/dashboard/api/routes.py (9 locations)
Impact:        Information leakage to dashboard clients. Mitigated somewhat by
               localhost-only binding (127.0.0.1 default), but not acceptable
               for production hardening.
Fix Applied:   Removed "detail": str(e) from all 500 responses. Errors are still
               fully logged server-side via logger.error().
Test Required: Existing dashboard API tests verify 500 response shape.
Status:        RESOLVED
